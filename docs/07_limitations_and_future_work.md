# Limitations, Risks and Future Work

Honest scope statements are part of the acceptance criteria: the system is a
**decision-support prototype** on **synthetic data**, not a production ERP module.

---

## 1. Modelling limitations

| # | Limitation | Consequence | Mitigation in this submission |
|---|---|---|---|
| L1 | Safety stock uses **demand variability only** — no `σ_L` (lead-time variability) term | a supplier that is sometimes late is under-penalised | supplier lead-time CV is measured and reported; the grade feeds the sourcing discussion |
| L2 | Daily demand assumed **independent** (`σ·√L`) | positively autocorrelated demand understates the buffer | stated as assumption A7, tested by construction (`test_zero_variability_gives_zero`) |
| L3 | Suggested quantity is an **order-up-to level** | ignores MOQ, pack size, container loads, budget | EOQ implemented for reference only; quantity is explicitly a suggestion |
| L4 | **Open POs are trusted** | a stalled open PO overstates the inventory position and hides a stockout | one SKU in the data has a stalled PO; the report lists it as a limitation |
| L5 | **Single warehouse**, single supplier per SKU | no multi-location allocation, no split sourcing | described in scope (D1 §4) |
| L6 | Purchase orders are **single-line** | mixed POs need manual splitting | documented schema simplification (D2 §2.3) |
| L7 | Cost model uses **unit cost only** | no holding/ordering/stockout-penalty cost, so no cost-optimal policy | turnover chart gives the cash-side view instead |
| L8 | 90-day demand window | seasonality longer than the window is invisible | window is a parameter (14–730 days); sensitivity grid included |
| L9 | Forecast is **univariate** | no promotion, price, weather or competitor signal | baseline comparison keeps expectations honest |
| L10 | Single 28-day **hold-out** | one lucky/unlucky period can decide the winner | only adopt a model if it beats the baseline by > 5 % |
| L11 | No `σ_L`/service-level optimisation per SKU class | same service level applied to all SKUs | ABC class is computed and printed for a future class-based policy |
| L12 | Manual stock counts are recorded as `ADJUSTMENT` rows | a count that is never entered leaves the ledger wrong | the API blocks movements that would make the balance negative |

## 2. Data limitations

* **Synthetic data.** Generated by `scripts/generate_seed_data.py`, so the
  distributions are plausible but invented. Results demonstrate the *method*, not a
  real business outcome.
* **No promotions/pricing history**, so demand spikes appear as noise rather than as
  explainable events.
* **No returns stream separated from demand** (`RETURN` exists in the schema but the
  generator does not use it), so net demand equals gross demand.
* **Zero-fill assumption (A2).** Days missing from `demand_records` count as zero
  demand. If the real cause is a reporting gap, averages are understated.

## 3. Engineering limitations

| # | Limitation | Note |
|---|---|---|
| E1 | No authentication/authorisation | intended to run on a trusted host or behind a gateway; every write endpoint would otherwise need a token |
| E2 | In-process analytics cache (8 entries) | fine for a single analyst; a multi-user deployment needs a shared cache or pre-computed snapshots |
| E3 | Analytics endpoints recompute on each parameter change (~4 s with forecasting) | acceptable for 24 SKUs; thousands of SKUs need pre-aggregation and a job queue |
| E4 | No pagination on analytics payloads beyond `limit` | the portfolio is small; larger portfolios should stream |
| E5 | Charts are PNG snapshots, not interactive | deliberate: the brief asks for chart *images* with titles, units and interpretation |
| E6 | Tests require a database for the integration half | they skip with an explicit reason when MySQL is unreachable |
| E7 | No migrations tool (Alembic/Flyway) | `sql/schema.sql` is the single DDL source; schema changes are applied manually |
| E8 | No rate limiting / request size guard beyond Flask's 8 MB body limit | a gateway or proxy would normally handle this |

## 4. Future work (prioritised)

### High value

1. **Lead-time variability in safety stock**
   `SS = z · sqrt(L·σ_d² + μ_d²·σ_L²)` — directly addresses L1 and is computable from
   the PO history already stored.
2. **Rolling-origin backtest** (e.g. 12 four-week folds) instead of a single hold-out,
   reporting mean and spread of MAE/MASE.
3. **EOQ/MOQ-constrained order quantity**: `Q = max(MOQ, round to pack size of
   order-up-to gap)`, weighted by ABC class and shelf life.
4. **Class-based service levels**: A = 99 %, B = 95 %, C = 90 %, with the cost of each
   policy quantified.
5. **Scheduled runs + alerting**: a cron job calling `POST /api/analytics/run` and
   emailing the risk digest.

### Medium value

6. Multi-warehouse dimension on the ledger (`location_id`) with transfer suggestions.
7. Purchase-order header/lines normalisation for multi-product POs.
8. Promotion/calendar regressors in the forecast (SARIMAX with exogenous inputs).
9. Interactive dashboard (Flask + Chart.js or a small React front end) reading the
   same endpoints.
10. Auth: token-based access with role separation (reader / planner / admin).

### Nice to have

11. Stockout-cost and holding-cost parameters to make the ROP economically optimal.
12. Supplier scorecard PDF per supplier, generated from the existing KPI endpoint.
13. Data-quality report (duplicate SKUs, negative balances, orphan rows) exposed as
    `/api/quality`.

## 5. Risk register (for the viva)

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Database unavailable during the demo | medium | high | pre-generated charts + report; `/api/health` degrades to 503; seeded SQL can be reloaded in seconds |
| Examiner asks for a formula not implemented | low | medium | every formula is in `analytics/formulas.py` with a docstring and a unit test |
| Examiner questions data authenticity | medium | low | generator script, planted edge cases, README §9 |
| "Why not just use Excel?" | high | low | audit trail (`analysis_runs`), reproducible config, validation, automated tests, API integration |
| Time overrun in the demo | medium | medium | run sheet with time boxes and cut-points (`docs/06` §7) |
